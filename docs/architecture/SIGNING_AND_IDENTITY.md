# Apple Signing and Identity (checkpoint `8155901`)

This describes the signing system that is frozen at this checkpoint. **Do not weaken any check listed
here** while fixing `VEYA-TEAM-032` (see [PERSISTENCE_AND_EVIDENCE.md](PERSISTENCE_AND_EVIDENCE.md)).

## Lifecycle overview

```
Apple Account (SRP + 2FA, in-process)          ──► session (dsid + Xcode-scoped token)
   └─ listTeams → exactly one Personal Team     ──► authorizedTeamIdentifier (backend, in memory)
signingKey  : RSA-2048 generated by Veya, AES-256-GCM PKCS#8 at rest, wrapping secret per installation
certificate : CSR from that key → Apple issues DER → proven by Apple inventory SPKI match
profile     : register device + App IDs → download main/runner profiles → validate offline
payload     : stage shipped .app → rewrite bundle IDs → sign in process → independent verify
application : install → installation_proxy inventory shows bundle/version/team
developerSupport launch probe: iOS accepts or refuses the signer (Developer Trust)
```

## 1. Apple authentication and session

- Backend: `LiveApplePersonalTeamBackend` (`macos/Sources/IOSSimMacCore/Services/ApplePersonalTeamLive.swift`),
  constructed as `.installationV2(...)` (`:3389`). The legacy identity store is retired.
- UI: **Sign In** calls `beginAuthorization(account:password:)` (`:3458`). The password is a
  `SensitiveInput`, cleared right after use (`DevelopmentInstallationModel.authorize`, `defer
  { secret.clear() }`). A 2FA code goes through `submitVerification(code:)` (`:3501`). The GrandSlam
  SRP stages (`APPLE_AUTH_STARTED`, `SRP_COMPLETE_ACCEPTED`, `M2_VERIFIED`, `SPD_DECRYPTION_SUCCEEDED`,
  `APPLE_SESSION_READY`) are recorded as secret-free structural diagnostics in `apple-diagnostics.json`.
- Session envelope (`LiveSessionEnvelope`): `dsid`, `xcodeToken`, `tokenExpiresAt`. It is stored by
  `KeychainAppleAuthorizationSessionStore` (`ApplePersonalTeamExperimental.swift:132`) as
  `authorization-session.v2.enc`, sealed with a wrapping secret (Keychain service
  `com.veya.authorization-wrap.v1`, fixed account UUID `5645594A-…-000000000002`). It is **one session
  per macOS user**, not keyed by Apple Account.
- **Development session:** the store is built with `KeychainWrappingSecretStore(kind: .unavailable)`,
  so `persistsAcrossLaunches == false`. The session lives only in the process, and every relaunch
  needs **Sign In** again.
- Session invalidation (`invalidateSession()`, and any non-protocol authentication failure in resume)
  sets `session = nil` and `authorizedTeamIdentifier = nil`, and removes the stored file.
  Protocol-shape drift preserves the session (`authenticationProtocolMismatch`).

## 2. Team discovery

- `listTeams(using:)` (`ApplePersonalTeamLive.swift` ~`:3970`): Apple `listTeams` → validated →
  Personal Teams only. None → `noTeam` (`VEYA-TEAM-030`). More than one → `personalTeamAmbiguous`
  (`VEYA-TEAM-031`). Otherwise **`authorizedTeamIdentifier = personal[0].id`**.
- `currentPersonalTeam()` (`:4661`) returns the team whose id equals `authorizedTeamIdentifier`.
- Every Developer Services mutation is guarded: `listRegisteredDevices`, `addDevice`,
  `registerIdentifiers`, profile creation and `downloadDevelopmentProfile` all require
  `authorizedTeamIdentifier == teamID`, else `.invalidTeam` → `VEYA-TEAM-032`
  (`AppleDomainFailure.map`, `AppleDomains.swift:61`).
- `AppleAccountContext` (`AppleDomains.swift:83`) caches the team **per composition** (one button press).

## 3. Signing key

- `VeyaSigningKeyStore` (`macos/Sources/IOSSimMacCore/Installation/SigningKeyStore.swift`): RSA-2048
  generated by Veya. At rest it is PKCS#8 encrypted with AES-256-GCM in
  `secrets/signing-keys/<keyID>.vkey` (mode 0600, directory 0700, symlink/permission checked). The AAD
  binds `magic|version|installationID|keyID|algorithm|publicKeySHA256`.
- Wrapping secret: **one per installation ID**. `KeychainWrappingSecretStore.baseQuery` (`:113`) uses
  generic password, service `Self.service`, account = `installationID`, non-synchronizable, data
  protection keychain with `interactionNotAllowed` (or UI-fail on the legacy keychain).
  `WrappingSecretBackendKind.select` (`:59`) returns `.dataProtectionKeychain` only when the running
  code has a Team ID and an access group under it, otherwise `.unavailable` (`VEYA-KEY-001`). **Every
  ad-hoc build, including this checkpoint, is `.unavailable`.** This is the M4 pre-release blocker.
- Development session: `DevelopmentMemoryWrappingStore` holds the wrapping key in memory. Ciphertext
  may persist, but after a relaunch the old key can't be unwrapped (`wrapperMissing` → `invalid` →
  replaced by a new key). Physically observed: after the 13:43:56 relaunch, signing key gen 147 was
  created at 13:44:34.
- The private key leaves the store only inside closure-scoped buffers: `withUnlockedPKCS8` for signing
  (bytes are zeroed afterwards) and `certificateSigningRequest` (an in-memory `SecKey`). **No SecKey,
  SecIdentity or certificate is ever added to a Keychain.**
- Retiring signing-key records are kept in the journal **forever**. Their SPKI digests are the only
  proof that a certificate belongs to this installation (`applyRetention`).

## 4. Certificate

- `CertificateDomain` (`AppleDomains.swift:233`) + `CertificateReconciler`/`CertificatePlanner`
  (`CertificateReconciliation.swift:125,193`).
- **Ownership is cryptographic only.** A certificate belongs to this installation iff its SPKI SHA-256
  equals a public key this installation generated. Names, serials, team membership and recency never
  authorize a revocation. `OwnedObsoleteCertificate` can only be constructed by the planner, from a
  retired key's SPKI that is not currently referenced.
- Decision: reuse an inventory certificate with the signing key's SPKI and ≥ 72 h left → otherwise
  issue (≤ 2 attempts per transition, budget shared across engine retries through
  `CertificateBudgetLedger`) → on Apple capacity (7460): refresh the inventory and revoke **one** owned
  retired-key certificate, only with `destructiveOwned` permission, then issue again → otherwise
  `VEYA-CERT-046` (the user must revoke one).
- Proof: Apple's live `listAllDevelopmentCerts` must list the same serial, DER SHA-256 and SPKI with
  ≥ 72 h left → `appleInventorySPKIMatch`, valid for `min(24 h, expiry − 72 h)`.
- Physically observed at 13:44:35 (8155901 run): `submitDevelopmentCSR` → `CERTIFICATE_LIMIT_REACHED`,
  then reconciliation completed and certificate gen 148 was promoted.

## 5. Profiles

`ProfileDomain` (`AppleDomains.swift:384`), binding = active certificate (team from its metadata, DER),
selected device (`EngineDeviceSelection.udid/name`), and bundle IDs derived from the team.

Bundle identifiers (`PersonalTeamBundleIdentifierSet(teamIdentifier:)`, `PersonalTeamProvisioningPOC.swift:91`):
`com.personalteam.iossim.t<first 12 hex of SHA-256("IOSSimPersonalTeam:<TEAM>")>` + `.on-device-dvt-poc`
(main), `.location-control-uitests` (UI tests), `.location-control-uitests.xctrunner` (runner). The
bundle IDs are therefore **a pure function of the Team ID**.

Transition: `account.team().id` must equal the certificate's team (**else `VEYA-TEAM-032`**,
`AppleDomains.swift:505`) → `ensureDeviceRegistered` → `ensureAppIdentifiers` → download main and
runner profiles → validate each → store.

### Offline profile validation (Swift, every observation and before staging)

`validateDevelopmentProfile` → `decodeAndValidateProfile` (`ApplePersonalTeamLive.swift:3075`) via
`developmentProfileContent` (`:3050`):

| Check | Rule |
|---|---|
| CMS | `CMSDecoder` decodes; signer status `valid` under `SecPolicyCreateBasicX509()` with `evaluateSecTrust = false`. **This checks the CMS signature itself, not a chain to an Apple root.** The Apple anchor is enforced in the signer (below). |
| `TeamIdentifier[0]` | == certificate's team |
| `ApplicationIdentifierPrefix[0]` | == team |
| `Entitlements.application-identifier` | == `TEAM.<exact bundle id>` |
| `get-task-allow` | `true` |
| `ProvisionedDevices` | non-empty, contains the selected UDID; `ProvisionsAllDevices != true` |
| `CreationDate` / `ExpirationDate` | `CreationDate ≤ now < ExpirationDate` |
| `DeveloperCertificates` | contains a DER whose SHA-256 equals the active certificate's |

`profileCMSBindingValidation` evidence is valid until `expiry − 48 h`. Free-team profiles last 7 days.

## 6. Payload signing (in process)

- Plan: `ShippedPayloadPlanProvider.plan` (`ShippedPayload.swift:101`) requires an active key, an active
  certificate (team + DER), and an active profile whose `certificate` metadata equals the certificate
  digest.
- Planned Info.plist rewrites only: main `CFBundleIdentifier` and `IOSSimGate3RunnerBundleIdentifier`;
  runner `CFBundleIdentifier`; the embedded `.xctest` `CFBundleIdentifier`. `approvedGraph` requires the
  staged signable graph (node kinds and paths) to equal the shipped source's, with the planned root
  identifier, else `VEYA-SIGN-026`.
- Requested entitlements (`ShippedPayloadPlanProvider.entitlements`, `:157`) are exact:
  `application-identifier = TEAM.<bundle>`, `com.apple.developer.team-identifier = TEAM`,
  `get-task-allow = true`, and `keychain-access-groups = [TEAM.<bundle>]` only if the profile grants the
  key. The profile must grant `get-task-allow = true` (else `VEYA-PROFILE-035`).
- Signer: `veya-signing-core` (Rust, in the bridge dylib), `veya_signing_sign`:
  - `profile_cms::verify_and_decode` (`native/veya-signing-core/src/profile_cms.rs:10`): exactly one
    signer; `CMSDecoderCopySignerStatus` valid; `SecTrust` evaluated with **anchors = Apple roots only**
    (`apple_codesign::KnownCertificate::all_roots`), anchor-only, **no network fetch**; signer CN must be
    `Apple iPhone OS Provisioning Profile Signing` issued by `Apple iPhone Certification Authority`.
  - `reconcile_profiles_and_entitlements` / `reconcile_profile_dictionary` (`lib.rs:727`): profiles and
    entitlements must exactly cover the provisioned bundle graph (`.app`/`.appex`); validity interval;
    exactly one `TeamIdentifier`; `ApplicationIdentifierPrefix == [team]`; `DeveloperCertificates`
    contains the leaf SHA-256; the profile's `application-identifier` pattern authorizes
    `TEAM.<bundle>`; the requested `application-identifier` is exact; the requested team ID equals the
    profile team; every requested key is in Veya's allowlist (`allowed_entitlement`, `:861`) **and**
    granted by the profile. Wildcards count only for identifier-valued grants and are never accepted
    in requests. Nested profiles must share one team.
  - `verify_signed_entitlements` (`lib.rs:1010`): after signing, the entitlements embedded in each
    executable are re-read and compared with the request.
- Proof: `veya_signing_verify` on the staged output independently re-verifies every Mach-O signature
  and recomputes the inventory SHA-256, which must equal the record → `payloadIndependentVerification`.
- `/usr/bin/codesign` is never invoked (`PayloadTransaction.swift` header).

## 7. Installation and identity on the device

- `ApplicationDomain` proves via installation_proxy `Lookup`: bundle id, version, and a team identifier
  read from the device's own view of the signature (`TeamIdentifier`, the signed team-identifier
  entitlement, or the `application-identifier` prefix, `application_team_identifier` in the bridge).

## Guarantees that let Developer Trust exclude signature and entitlement causes

iOS reports invalid signature, inadequate entitlements and untrusted developer with the same launch
denial (`FBSOpenApplicationErrorDomain 3 Security`). Each prerequisite in
`DeveloperTrustPrerequisites` rules out one of the other causes with evidence Veya produced itself:

| Prerequisite (journal evidence) | What it proves | Which alternative cause it removes |
|---|---|---|
| `payloadSignatureVerified` (`payloadIndependentVerification` on the active payload) | Every Mach-O in the installed payload carries a valid signature, independently re-verified after signing | "Invalid code signature" |
| `profileBindingValidated` (`profileCMSBindingValidation`, unexpired) + signer-side checks | The embedded profile is Apple-signed (anchor enforced in `veya-signing-core` at sign time), unexpired, for this team, App ID prefix, exact application identifier, this device, this certificate; `get-task-allow` granted | Wrong team, unprovisioned device, expired profile, wrong App ID |
| (Signer entitlement reconciliation, a precondition of any payload) | No entitlement is signed that the profile does not grant; embedded entitlements re-read and matched | "Inadequate entitlements" |
| `certificateInventoryMatched` (`appleInventorySPKIMatch`, unexpired) | Apple currently lists this exact certificate for the key Veya controls | Revoked or unknown certificate |
| `applicationInstalled` (`deviceInventoryAfterInstall`) | The exact bundle/version/team is installed on this device | App missing or different |
| `developerServicesProven` (call-site guarantee) | CoreDevice/RSD/AppService answered on this connection right before the launch | DDI, transport, Developer Mode |

Remaining caveat, stated honestly: the Swift-side `profileCMSBindingValidation` check alone does not
anchor to Apple. The Apple anchor is enforced by the signer on the bytes that were signed into the
payload. Any profile that reaches the device has passed both checks.

## What is not done, by design

- Veya never signs in for the user, never stores the Apple password, never adds keys or identities to
  the login keychain, and never uses `codesign` or `security cms`.
- Veya never revokes a certificate it cannot prove it owns.
- Veya never trusts a developer on the device (AMFI action 4 is not exported).
