## A. Apple authorization session storage (security defect, fixed)

**Finding (P1, SECURITY):** auth v1 saved the Apple session (`authorization-session.enc`, AES-GCM) under a
key read directly from `authorization-keychain.secret`, a `0600` plaintext file in the same
`~/Library/Application Support/IOSSim/` directory. The custom `Veya-Authorization.keychain-db` used the same
file as its password, and "quarantine" copied that plaintext key to `*.quarantine-*`. At rest this is
equivalent to plaintext for any same-user process, backup, or copied folder. `.completeFileProtection`
has no effect on macOS. On the development Mac these v1 files exist today (`authorization-keychain.secret`,
one quarantined copy, `authorization-session.enc`).

**Auth v2 (implemented, `ApplePersonalTeamExperimental.swift`):**
- Session plist sealed with AES-256-GCM (AAD binds schema/service/account) in `authorization-session.v2.enc`, `0600` in a `0700` dir, atomic rename.
- The 32-byte key is a separate wrapping secret in the **same fail-closed backend as M4** (`KeychainWrappingSecretStore`), under its own service `com.veya.authorization-wrap.v1` and label, so it never shares an item with signing keys.
- Backend `unavailable` (every ad-hoc/LOCAL_TEST build, until M4 is resolved): the session stays **in memory only** for the launch. Nothing credential-bearing reaches disk and the user signs in again after relaunch. There is no weaker at-rest fallback.
- Tampered file, foreign file, or missing wrapper: the file is discarded and sign-in is required (fail closed, no prompt).
- v1 artifacts, including quarantined copies, are deleted on every load/save/remove. When the v2 backend is available they are first re-sealed into v2. The v1 keychain is removed with `SecKeychainDelete` (drops it from the search list).
- Deviation from spec 08: spec 08 stores the session itself as a DP-Keychain item. v2 keeps the ciphertext in a file wrapped by a DP-Keychain key. The security boundary is the same (the DP Keychain), and one backend serves M4 and auth. The legacy login-keychain item `com.iossim.mac.apple-authorization` is no longer read; M8 inventories it.

**Tests (`AppleAuthorizationKeychainRegressionTests`, 5/0, SecurityAgent never launched):** round trip with no
plaintext/metadata in the file and no key file beside it; unavailable backend writes nothing and purges v1
plus quarantine copies; v1 → v2 migration then deletion; tamper and missing-wrapper fail closed; packaged
`IOSSimAuthDiagnostic` create/read/update/read/remove across relaunches without prompt; production
selection on the ad-hoc helper reports `unavailable persists=false`.

## B. Certificate reconciliation (spec 07; new, unrouted)

`Installation/CertificateReconciliation.swift`:
- Ownership is **cryptographic only**: a certificate's SPKI SHA-256 (derived from its DER, never from Apple text) must equal a public-key digest generated by this installation's key store. The digests come from the journal's `.signingKey` records, and retiring records are never dropped.
- Only certificates of **retired** keys that no active or candidate record references are reclaimable. Names, `machineId` markers, metadata serials, team, and recency never authorize revocation.
- `revoke` takes `OwnedObsoleteCertificate`, whose initializer is `fileprivate` to the planner, so revoking an unknown certificate cannot be expressed.
- Hard limits: 2 issue attempts, 1 revocation, and an inventory refresh after capacity rejection and after revocation. A lost issue response is resolved on rerun by SPKI match, not by blind reissue. An issued certificate whose SPKI doesn't match fails closed (`VEYA-CERT-042`). Contradictory inventory fails closed (`VEYA-CERT-040`). No reclaimable certificate returns user-safe `VEYA-CERT-046`.

**Tests (`CertificateReconciliationTests`, 10/0):** exact call sequences for reuse, issue, renewal-window
replacement, reclaim-one-then-retry, never revoking unknown/other-Mac/referenced certificates, at most
1 revoke and 2 issues, contradiction, mismatched issuance, ambiguous issue, and journal-derived key facts.
**Real-DER cross-check:** the certificate SPKI digest equals both `VeyaSigningKeyStore.publicKeySHA256` and
OpenSSL's independent SPKI encoding.

**Build 11 comparison:** the shipping `LiveApplePersonalTeamBackend` reclaim still classifies ownership by
local metadata record or Apple `machineId` (P1/P2 in `CertificateOwnership`). That is weaker than spec 07,
and it is replaced when the new planner is routed (M7 production composition / M11 removal).

## C. Live Apple-flow integration (continuation)

`.authorization`, `.team`, `.certificate` and `.profile` are production engine domains (`Installation/AppleDomains.swift`):

- `AppleDeveloperServices` is implemented by `LiveApplePersonalTeamBackend` (stateless extension in
  `ApplePersonalTeamLive.swift`): list/submit-CSR/revoke certificates, register device, register App IDs,
  download profiles, all over the existing authenticated `developerRequest` transport.
- `LiveApplePersonalTeamBackend.installationV2()` is the only backend the production composition builds. Its legacy
  identity store is `RetiredLegacyIdentityKeychain`, which refuses every call, so `prepareIdentity`/codesign probes
  are unreachable from the new route.
- CSR: generated from the key-store key inside `withUnlockedPKCS8` → in-memory `SecKey` (no Keychain item).
- `.authorization`/`.team` are observation-only: no stored v2 session → `waitingForUser` "Sign in…"; the helper
  never signs in. Network/rate/protocol failures are typed (`VEYA-AUTH-031/032/033`, `VEYA-TEAM-030/031/032`).
- `.certificate`: DER stored content-addressed under `certificates/`; satisfied only if the DER parses, its SPKI is
  the current signing key, and ≥72 h validity remains. Proof = Apple inventory lists exactly this DER for our SPKI;
  proof lifetime 24 h, so a certificate revoked elsewhere is detected and replaced. Revocation requires the run's
  capability manifest to grant `destructiveOwned` (spec 07); otherwise capacity is `VEYA-CERT-046`.
- `.profile`: main + runner profiles for the team-derived bundle IDs, bound to the active certificate DER, the
  selected iPhone UDID and the team; validated offline (CMS) on every observation; replaced 48 h before expiry,
  on certificate change, and on device change. A profile that does not match is never staged.
